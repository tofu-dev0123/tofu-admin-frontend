argument-hint: <トピック>

バグのトピック `$ARGUMENTS` について、原因・影響調査から Issue 起票までを行う。
フロー全体は `.claude/rules/dev-flow.md` を参照。

## 1. トピックの確認

- `$ARGUMENTS` が空、または症状が分からないほど曖昧な場合は、以下をユーザーに確認する
  - どの画面・操作で起きるか（URL・デバイス幅・ブラウザ）
  - 期待する動作と実際の動作（エラーメッセージ・コンソールログ・スクリーンショット）
  - 発生環境（local / dev 環境 / 本番）
- 似た Issue がないか `gh issue list --state all --search "<キーワード>"` で確認し、あれば提示する

## 2. 原因・影響調査（コードを読む）

推測で済ませず、実際に既存コードを読んで以下を明らかにする。

- **再現条件**: 発生する入力・状態・画面幅・タイミング（初回表示 / 遷移後 / ハイドレーション後など）
- **原因**: 原因箇所（`file:line`）と理由。特定できない場合は仮説と、確認に必要な情報
  - 再現確認が必要なら既存テストや `pnpm exec vitest run` で一時的に確かめる、または `pnpm dev` で画面を確認する（調査用ファイルはコミットしない）
- **影響範囲**: 影響する画面・コンポーネント・hooks・Context・ストア。プロキシ Route（`src/app/api/admin/**`）・バックエンド API・`src/types/api/` への影響の有無
- **テスト**: 既存テストで検出できなかった理由と、追加すべき再現テスト（UT で再現できない場合は目視確認手順）

## 3. 改修案の提示

調査結果と改修案をユーザーに提示する。

- 調査結果（上記の各項目。根拠となる `file:line` を添える）
- 改修案（修正方針、変更するファイル、再現テストの概要）
- 選択肢がある場合は推奨案と理由を示す
- 未決事項があれば質問としてまとめる

ユーザーの指摘を受けたら調査・案を修正して再提示する。**ユーザーが内容を確定するまで起票しない。**

## 4. 起票

1. `.github/ISSUE_TEMPLATE/bugfix.md` を読み、frontmatter と `<!-- -->` コメントを除いた見出し構成に沿って本文を作成する
2. タイトル案（日本語、70 文字以内）と本文案を提示し、承認を得る
3. 承認後、本文を一時ファイルに書き出して起票する

   ```bash
   gh issue create --title "<タイトル>" --body-file <一時ファイル> --label bug
   ```

4. 作成された Issue の URL を表示し、実装に進む場合は `/implement <番号>` を案内する
